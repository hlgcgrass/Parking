# 停车小程序后端 · 全量搬数据库方案（v2，已采用）

> **决策反转**：前一轮评估推荐"基础数据内存 + 管理员增量走数据库"的混合架构；
> 本轮用户明确改为**全量搬数据库**——理由是现有 json 大部分数据不可用、后续要清理，
> 且希望数据源统一成「接口查询」，不再把数据写死在代码包 json 里。
> 本文件为最终落地方案，云函数代码已按此重写。

---

## 一、架构总览

```
┌─────────────┐   add/update/remove    ┌──────────────────────────┐
│ 小程序前端   │ ─────────────────────▶ │ 云函数 parking（接口层）   │
│ (api.js 不变)│                        │  - 只读 action 查数据库     │
└──────┬──────┘ ◀───────────────────── │  - 写 action 写数据库       │
       │ 查询/列表/详情/搜索/附近        └───────────┬──────────────┘
       │                                            │ 权威数据源
       │                                   ┌────────▼───────────────┐
       │                                   │ 云数据库（CloudBase）    │
       │                                   │  p_meta / p_places      │
       │                                   │  p_parkings / p_tips    │
       │                                   │  p_users / p_favorites   │
       │                                   │  p_likes / p_reports ... │
       │                                   └────────────────────────┘
       │
  （推荐）端上缓存：首次拉全量静态数据 → wx.setStorage
       之后搜索/排序/距离/详情在端上算，仅个性化与写操作走接口
```

**核心机制：数据库权威源 + 云函数实例 version 缓存**
- 静态数据（地点/车场/攻略/城市/分类）权威源 = 云数据库。
- 云函数实例内按 `p_meta.version` 缓存到内存；管理后台改库后 `bumpVersion()` 改 version，
  下次请求自动重载——**改数据即时生效，无需重新部署云函数**（这正是比"写死 json"强的地方）。

## 二、集合模型（字段映射）

| 集合 | 来源 | 关键字段 |
|---|---|---|
| `p_meta` | data.json 的 meta + cities + categories | `cities[]`、`categories[]`、`exported_at`、`fee_rules`、`version`(缓存失效键) |
| `p_places` | data.json.places（54） | 原 place 全部字段 + `id`(int) 业务主键 |
| `p_parkings` | data.json.parkingsByPlace 展平（113） | 原车场字段 + **`place_id`**(int) + `fee_rules[]` |
| `p_tips` | data.json.tipsByPlace 展平（54） | `place_id`(int)、`category`、`content`、`source`、`status`(`ok`) |
| `p_users` / `p_favorites` / `p_likes` / `p_reports` / `p_search_logs` | 原有 | 不变 |

> 车场的 `tips`（车场级）与 `p_tips`（地点级攻略）两套并存，沿用旧逻辑。
> `place_id` 统一存 int，与 `p_places.id` 一致，查询/关联无类型坑。

|---|---|---|

## 四、数据导入（一次性）：`migrate` action

部署后，管理员在「云开发→云函数→parking→测试」或前端管理员页调用：

```js
wx.cloud.callFunction({ name: 'parking', data: { action: 'migrate' } })
```

该 action（admin 鉴权）从**代码包内 data.json** 覆盖写入 `p_meta/p_places/p_parkings/p_tips`，
返回 `{ places, parkings, tips }` 条数。之后运行时不依赖 data.json，可删除或保留作备份。

> 用途：你清理完源数据后，重新导出 data.json → 重新部署（或仅更新代码包 data.json）→ 调 migrate 重导。
> 日常小改请用下面的 admin CRUD，不必重新 migrate。

## 五、管理后台（清理 / 补充数据）：admin CRUD

鉴权：`ADMIN_OPENIDS` 环境变量白名单（部署后在云函数配置里设，逗号分隔多个 OPENID）。
`openid` 取自 `getWXContext()`，前端无法伪造。

| action | 作用 |
|---|---|
| `admin-upsert-place` | 新增/更新地点（`data:{id,...}`） |
| `admin-upsert-parking` | 新增/更新车场（`data:{id, place_id, ...}`） |
| `admin-upsert-tip` | 新增/更新攻略（`data:{place_id, category, content, source}`；带 `_id` 为更新） |
| `admin-delete-place` | 删除地点（`_id`） |
| `admin-delete-parking` | 删除车场（`_id`） |
| `admin-delete-tip` | 删除攻略（`_id`） |

每次写操作后自动 `bumpVersion()`，云函数实例缓存立即失效重载，**前端下次请求即见最新数据**。

> 拿不到 OPENID？可临时在云函数测试里用 `action:'user'` 的返回 `userId` 字段，就是你自己的 OPENID。

### 五点一、批量删除旧地点

新增云函数 action：`admin-delete-places`。接口只接受明确的 `place_ids` 或完全匹配的 `place_names`，不提供“无条件删除全部地点”的参数。

默认是预览模式，不会写库：

```js
wx.cloud.callFunction({
  name: 'parking',
  data: {
    action: 'admin-delete-places',
    data: { place_ids: [1, 2, 3] }
  }
});
```

确认预览结果无误后，才使用真实删除参数：

```js
wx.cloud.callFunction({
  name: 'parking',
  data: {
    action: 'admin-delete-places',
    data: {
      place_ids: [1, 2, 3],
      dry_run: false,
      confirm: 'DELETE_SELECTED_PLACES'
    }
  }
});
```

真实删除会同步删除这些地点下的 `p_places`、`p_parkings`、`p_tips`，并清理关联车场的收藏和点赞记录；不会删除用户账号、反馈日志或云存储图片。地点 ID/名称有任何一个未匹配时，会拒绝部分删除，避免误删。

### 五点二、批量新增整理后的攻略

新增云函数 action：`admin-import-guides`。接口默认也是预览模式，只允许新增，不会覆盖已有的地点名称或业务 ID。坐标可以暂时为空，但应将 `coordinate_status` 标记为 `待补充`，不能用目的地中心坐标代替停车场坐标。

预览：

```js
wx.cloud.callFunction({
  name: 'parking',
  data: {
    action: 'admin-import-guides',
    data: {
      places: [{
        name: '北京路',
        category: '景点',
        city_code: '440100',
        parkings: [{
          name: '北京路天河城地下停车场',
          fee_detail: '10元/小时；会员每月3小时优惠；超出后5元/30分钟',
          guide_text: '机械车位较多，节假日入口容易排队。',
          location: '导航“北京路天河城地下停车场”',
          fee_rules: [
            { rule_type: 'normal', price: 10, unit: 'hour', unit_minutes: 60, description: '常规收费' }
          ]
        }]
      }]
    }
  }
});
```

预览返回自动分配的地点/车场业务 ID、地点数、车场数、攻略数和收费规则数。确认无误后，在同一个 `data` 对象中增加：

```js
dry_run: false,
confirm: 'IMPORT_GUIDES'
```

支持的主要字段：地点使用 `name/category/address/district/lng/lat/summary/tags/area_tips`；车场使用 `name/fee_detail/guide_text/location/lng/lat/fee_rules/daily_cap/night_flat/confidence`。`guide_text` 会写入车场的 `tips`，`fee_detail` 会保留为车场收费摘要，`fee_rules` 会用于价格排序。

小程序端已提供 `api.adminDeletePlaces(data)` 和 `api.adminImportGuides(data)` 两个调用封装；这两个管理接口固定走微信云函数，并且仍受 `ADMIN_OPENIDS` 白名单限制。

## 六、端上缓存（必做 · 降本关键）

全量搬数据库后，若每次只读 action 都查库，DAU 1000 × 15 次/天 ≈ 45 万次读/月，会打穿基础套餐（20 万）。
**必须做端上缓存**：

1. 小程序启动 / 首次进入时，调一次 `places` + `cities` + `categories` 拉全量静态数据，存 `wx.setStorage`（带 `version`/`exported_at` 时间戳）。
2. 搜索 / 排序 / 距离 / 详情 全部在端上用本地数据计算（复用云函数现有内存逻辑的同款算法）。
3. `version` 变化时（health 接口比对）才重新拉全量。
4. 只有收藏 / 点赞 / 我的 / 写操作 走接口。

这样数据库读降到「几乎只有写 + 个性化查询」，成本可控，且首屏更快、弱网可用。
**这是全量搬数据库能成立的必要配套，不能省。**

## 七、部署步骤

| # | 动作 |
|---|---|
| 1 | 前端 `utils/config.js` 的 `CLOUD_ENV` 占位符（`cloud1-0gplaceholder`）→ 替换为你真实的云开发环境 ID |
| 2 | IDE 右键 `cloudfunctions/parking` → 「上传并部署：云端安装依赖」 |
| 3 | 云函数配置 → 环境变量 → `ADMIN_OPENIDS=你的OPENID` |
| 4 | 调 `action:'init'`（建集合）→ 调 `action:'migrate'`（导入静态数据） |
| 5 | 小程序端加「端上缓存层」（见第六节）；管理员页接 admin-* action |

## 八、成本测算（含端上缓存）

- 假设 DAU 1000，每人每天 15 次页面交互：
  - 端上缓存后，静态读 ≈ 每人每天 1 次全量拉取（version 不变则 0）→ ~3 万次/月
  - 个性化（收藏/点赞/我的）≈ 每人每天 3 次 → ~9 万次/月
  - 写（加攻略/收藏）极少
  - **合计 ≈ 12 万次/月 < 基础套餐 20 万，够用**
- 读放大已修：原 `place` 详情对每个车场逐个 `count()` 点赞（约 90 万/月）已改为
  `p_parkings.like_count` 字段 + 写入时 `db.command.inc(±1)` 维护，详情页直接读字段，不再逐车场查库。

## 九、回滚 / 兼容

- 前端 `api.js` 双通道仍在：若云环境出问题，可切回 HTTP 通道（需另起后端服务，仅兜底）。
- 旧内存版逻辑已整体替换为数据库驱动，无 data.json 运行时依赖；data.json 仅作 migrate 导入源。
- 若数据库数据清空，只读 action 返回空列表（不崩，已容错）。
