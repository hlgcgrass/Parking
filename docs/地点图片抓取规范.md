# 地点图片抓取规范

## 1. 适用范围

本规范适用于停车攻略中的目的地、商圈、景区、医院、公共文化设施及其后续新增地点的封面/形象图。

每个地点默认配置 1 张主图。主图的任务是让用户在列表或详情页中一眼认出“这是哪里”，不是单纯提供一张泛化的城市风景图。

## 2. 检索要求

### 2.1 关键词

使用“广州 + 地点全名 + 外景/正门/地标/招牌/夜景/航拍 + 横屏”等组合关键词。地点有别名、院区或分店时，必须把别名和具体院区写入检索词。

示例：

- `广州 北京路步行街 牌坊 外景 横屏`
- `广州 天环广场 PARC CENTRAL 正门 横屏`
- `广州 中山大学附属第一医院 院名 楼体 外景 横屏`

### 2.2 渠道

图片搜索渠道可使用百度图片、Bing 图片、Google 图片或其他能返回原图页面的检索服务。优先使用能够按热度、浏览量、收藏量或综合排序查看结果的渠道；排序信息可见时，先取排名靠前的一组候选，再做人工筛选。若渠道不公开浏览量，则使用该渠道的默认相关性排序，并结合来源权威性、图片质量和更新时间判断，不得伪造热度数字。

图片搜索页只用于发现候选图，不能把搜索结果页当作来源。必须打开原始页面，记录原图 URL、来源页 URL、作者/机构、许可或使用依据。

优先顺序：

1. 地点官方、政府、景区或医院官网及官方公众号文章；
2. 具备明确授权的图片库或开放许可图片（例如 Wikimedia Commons）；
3. 新闻媒体、旅游平台、地图/点评平台的公开图片，仅在项目具备相应使用权限或仅作内部演示时使用；
4. 无法确认作者、授权或原始页面的图片不得作为正式发布素材。

### 2.3 热度优先策略

对于广州塔、陈家祠、沙面岛、北京路、珠江新城等知名地标，优先选择公众长期认可的经典视角：即使画面没有地点名称，只要建筑轮廓、招牌、牌坊、桥梁、塔身或城市关系足够独特，也属于合格候选。不要为了出现文字而牺牲地标辨识度。

执行顺序：

1. 用地点全名和“经典、地标、夜景、航拍、打卡、全景”等词检索，并按热度/浏览量/综合排序取前 5～10 张；
2. 从中剔除竖图、低清图、严重水印和明显错图；
3. 对剩余图片按“看一眼能否认出地点”排序，再比较横屏构图、清晰度、主体完整度和来源可用性；
4. 选出 1 张主图，并保留来源页；不把“能看到地点名字”当成必选条件。

对于商场和医院等容易混淆的地点，热度排序仍需加一层身份核验：热门图必须能通过建筑外观、门头、院区特征或原始页面说明确认对应地点。

### 2.4 候选数量

每个地点至少检索 5 张候选图，至少保留 2 张横图进入视觉复核。若首轮没有合格图，应更换关键词或渠道，不得用不相关的竖图、地铁口或普通街景凑数。

## 3. 选图标准

### 3.1 必须满足

- 横屏构图；候选原图宽度建议不低于 1200 px，最低不得低于 600 px；入库时统一压缩到适合小程序首屏的尺寸和体积；
- 宽高比建议在 3:2 至 16:9 之间，列表裁切后主体仍完整；
- 图片主体与地点名称直接对应，能够看到楼体、正门、牌坊、招牌、独特建筑、核心景观或其他明显地标；
- 画面清晰、曝光正常、色彩自然，无明显压缩损坏；
- 适合作为小程序卡片/详情页首图，主体不要贴边，左右保留适当裁切空间；
- 采集日期或页面信息能够确认地点身份，避免使用已经拆除、改名或明显过时的建筑外观。

### 3.2 优先满足

- 地点名称或官方标识清晰可见；
- 建筑全貌与周边环境同时出现，方便用户判断入口和位置；
- 商圈使用最具代表性的主入口或整体天际线，而不是附近路口；
- 景区使用牌坊、核心建筑、招牌或最有辨识度的景观，而不是普通树林/湖面；
- 医院使用带院名的楼体、门头或正门，优先能区分院区的角度；
- 同一批图片在天气、色调和构图上保持基本统一。

### 3.3 禁止使用

- 与地点没有直接关系的地铁站、公交站、普通道路、泛化天际线；
- 只拍局部且无法辨认地点的建筑细节；
- 竖图硬裁成横图、严重拉伸、低清缩略图或带搜索页面 UI 的截图；
- 大面积水印、二维码、广告文案、平台 Logo 或影响主体识别的文字；
- 明显侵犯隐私的近距离人物、患者信息、车牌或内部就诊画面；
- 来源不明、原图页失效、无法确认授权或明显受限于防盗链的素材；
- 一张图重复用于多个不同地点，除非它确实同时表现同一地点组且页面文案已明确说明。

## 4. 来源与版权记录

每张入选图必须同时记录以下字段：

| 字段 | 要求 |
| --- | --- |
| `image_url` | 可访问的原图或稳定图片地址；不得填搜索结果页 |
| `image_source_url` | 原始文章、图片详情页或官方页面 |
| `image_credit` | 作者、机构、平台或许可信息；未知时不得臆造 |
| `image_alt` | “地点名 + 地点实景图”，必要时补充“正门/夜景”等说明 |
| `image_storage_path` / `cloud_path` | 按地点名保存，不能使用 `1.jpg`、`20.jpg` 等无语义文件名 |
| `image_review_note` | 可选；记录为何选中，例如“正门院名清晰”“牌坊辨识度高” |

优先选用允许再发布的素材。若使用新闻、旅游平台或用户上传图片，必须先确认项目的使用范围；不能因为图片搜索结果排名靠前就默认拥有转载权。

## 5. 素材处理与项目落盘

1. 下载原图或可用的高质量版本，确认文件真实格式和尺寸。
2. 必要时只做等比例缩放、轻度压缩和合理裁切，不改变地点标识，不添加项目水印。
3. 使用地点中文名作为文件名，例如 `广州塔（小蛮腰）.jpg`、`中山大学附属第一医院.jpg`。
4. 同步更新：
   - `parking-miniapp/utils/place-images.js`
   - `parking-miniapp/cloudfunctions/parking/place-images.js`
   - `parking-miniapp/cloudfunctions/parking/assets/place-images/`
5. 两份图片元数据中的地点 ID、文件名、来源、署名和图片地址必须一致；云端 `asset_path` 必须能指向实际文件。
6. 不覆盖用户自行新增的图片或与本次任务无关的素材；替换前先核对地点 ID 与地点名。

## 6. 质量检查

提交前逐张检查：

- 文件存在、可打开、宽度和宽高比符合要求；
- 入库图片以详情页快速打开为硬约束：最长边不超过 1024 px、单张必须不超过 100KB；超过时先等比缩放到 800 px，再用 JPEG 质量 45～78 压缩；压缩后仍超限必须判定失败，不允许进入资源目录；
- 缩略图中主体清楚，列表裁切不会切掉招牌/主楼/牌坊；
- 图片与地点一一对应，没有错图、旧图或重复图；
- 来源页可访问，作者/机构和许可信息没有编造；
- 小程序详情页首图能加载，加载失败时备用地址仍可用；
- 云函数部署后能从 `asset_path` 上传到对应版本化 `cloud_path`（当前为 `place-images/v3/`）；换批次时递增目录版本，写库成功后清理旧 `image_file_id`，不会因数字文件名或旧缓存继续显示旧图。

## 7. 批量处理与提速

地点数量较多时，采用“机器做重复劳动、人工做最终判断”的批处理方式：

1. 先批量生成每个地点的检索词和候选清单；每个地点抓取 5～10 张热门/高相关候选，不逐张处理到最终入库。
2. 将候选图生成联系表，人工只确认“地点是否正确、是否横屏、哪张最像该地点”三项；结果写回 `data/place-image-selections.json`。
3. 运行 `pwsh -File scripts/同步地点图片选择.ps1 -ThrottleLimit 8 -MaxWidth 1024 -MaxBytes 100000` 并行下载、校验尺寸、压缩并统一转为 JPEG；单张失败只记录失败项，不中断整批任务。
   只替换个别地点时可追加 `-Ids 16,20`，只处理指定 ID，避免重复下载整批素材。
4. 运行 `node scripts/生成地点图片映射.js`，一次性同步小程序端和云函数端的映射，避免手工改两份文件。
5. 仅对失败项补搜或重试，不重新处理已经通过校验的图片。默认并发 8；遇到来源站点限流时降为 3～4，避免触发封禁。

候选清单必须保留地点 ID、候选排名/热度（如页面公开）、图片地址、来源页和筛选结论。未公开热度的渠道不填写猜测值；“热门”只作为初筛依据，最终仍以地点辨识度和来源可用性为准。

最终交付应同时包含图片文件、元数据变更和本规范要求的来源记录，不能只替换一个远程 URL。
