# 小红书攻略数据整理规则（入库版）

> 版本：v1.2（增加地点级与停车场级定位要求）
>
> 适用范围：对已保存的小红书搜索页和笔记详情页原始 JSON 进行本地整理。
>
> 目标：每批笔记处理完成后，同时产出人工审核用 Markdown 和可直接调用 `admin-import-guides` 的 JSON。Markdown 仅用于阅读，不能代替 JSON 入库。

## 一、处理边界

1. 本阶段只处理本地原始 JSON，不重复打开已保存的笔记页面。
2. 一次完成页面噪声清除、停车事实提取、评论清洗、同名停车场合并、收费结构化和入库前校验。
3. 每个停车场必须形成最终四字段：停车场名称、收费明细、攻略正文、停车场定位；同时生成接口所需的 `fee_rules`、坐标状态、可信度和冲突标记。
4. 每个目标地点必须额外生成一段“地点级停车攻略总结”，汇总该地点全部已入选停车场的步行距离、入口、拥堵/排队、车位和车型限制等信息，落库到 `area_tips`，供详情页“停车攻略”区域展示。
5. 每条信息必须保留所属笔记、信息来源位置（正文/评论/标题）和原始文件路径，方便回溯。
6. 不能从图片中可靠读取的内容，不根据图片标题或上下文自行补全。

## 二、信息分层

### A. 正文明确信息

正文明确写出停车场名称、收费数字、免费时长、封顶价、优惠条件、入口、车位数量、路线或停车风险的信息，可以进入“可用信息”。

数字按原文保留，不擅自添加“约”。原文写“3小时内 7.5 元/小时”，保留为“3小时内 7.5 元/小时”；原文只写“大概”“上下”“看起来”，才保留不确定表述。

### B. 评论区停车线索

评论中涉及收费变化、封顶价、车位是否充足、是否需要预约、入口、道路拥堵、停车后步行等内容，进入“评论线索”，但不能直接升级为正式收费标准。

评论线索必须尽量保留显示日期；没有明确地点、时间或停车场名称的评论，只记录为低可信待核线索，不能用于最终合并。

### C. 标题信息

标题中的价格或结论只能作为“标题声称”保存。正文没有对应收费说明时，不得把标题数字直接写成停车场正式收费。

### D. 不采用信息

以下内容在第一层清洗中剔除：小红书页面框架、推荐流内容、作者互动、与停车无关的游玩/餐饮/购物内容、无法定位到目标地点的泛化价格、图片中无法读取的收费数字。

## 三、收费信息拆分规则

收费信息分为四类，不混写：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 正式收费表述 | 5元/小时、24小时最高45元 | 可进入正文明确信息 |
| 实付记录 | 停车3小时支付7.5元 | 标记为实付记录，不反推小时价 |
| 优惠/免费条件 | 充电满30分钟免费停车2小时 | 单独记录触发条件和限制 |
| 评论或标题线索 | 评论称白天更贵、标题称3小时7.5元 | 标记待核，不当正式价格 |

存在不同来源的收费冲突时，保留各来源原说法，并标记“收费冲突/待现场核实”，不平均、不择一覆盖。

## 四、停车点信息字段（内部中间层）

每个笔记内的候选信息暂按以下字段记录：

```text
parking_name        停车场名称或原文导航词
fee_facts           正文明确收费
payment_records     实际支付记录
discount_facts      优惠、免费和预约条件
access_route        入口、导航词、步行/接驳路线
capacity_status     车位数量、是否充足、是否排队
vehicle_limits      机械车位、新能源、车型等限制
parking_warnings    拥堵、满位、错峰、离场等注意事项
comment_leads       评论区待核线索
uncertainties       信息缺口、表述冲突和图片缺失
evidence_type       正文 / 评论 / 标题
source_note         原笔记标题、作者、发布时间、排名、收藏量、链接
raw_file             原始详情 JSON 路径
```

第一层清洗允许 `parking_name` 暂时是原文导航词，但不能把“附近”“周边”“某个停车场”等泛称当成正式停车场名称。

## 五、清洗后的展示格式

面向审核时，每篇笔记单独展示以保留审核链路；生成入库 JSON 时必须跨笔记合并同一停车场，避免重复建档：

```text
### 笔记 N：标题
- 抓取排名 / 收藏量：
- 正文可用信息：
  - 停车点：
  - 收费：
  - 优惠：
  - 路线与车位：
  - 注意事项：
- 评论区待核线索：
- 本篇不足：
- 原始文件：
```

## 六、审核原则

1. 先确认“这条信息是否真的属于珠江新城目标场景”，再确认收费数字。
2. 先保留来源差异，再决定是否跨笔记合并同一停车场。
3. 正文明确数字优先于标题数字；评论数字只能作为补充或冲突提示。
4. 充电免费、会员券、消费减免、预约价必须同时记录触发条件、时长/金额和限制。
5. “走几分钟”“从哪个门进”“是否机械车位”“是否容易排队”等会影响停车决策的信息应保留。
6. 不因为信息不完整而猜测停车场名称、坐标、封顶价或正式收费；缺失项按入库字段规则标记为待补充，并由自动校验拦截不可用记录。

### 6.1 严格噪声拦截

以下内容即使出现在正文或评论附近，也不得进入停车场名称、收费、备注或评论线索：

- 小红书用户名、作者昵称、头像旁的数字、点赞数、评论数、回复数和平台推荐流标题。
- “首页”“关注”“展开”“说点什么”“LIVE”、备案信息、版权信息等页面框架文字。
- 只有提问、没有事实内容的句子，例如“停车费是多少钱？”“哪里可以停车？”“需要预约吗？”。
- 没有答案或可验证事实的互动话术，例如“怎么约”“开放吗”“求问”“求推荐”“谢谢”“码住”“太贵了吧”。
- 与停车无关的情绪、闲聊、人物评价、消费推荐、游玩路线和泛化生活经验。
- 不能确认地点、停车场或收费背景的孤立数字，例如单独出现的“3.5”“60”“封顶”等。

### 6.2 信息量门槛

一条内容至少要提供以下任一项，才可以保留为停车信息：

- 可识别的停车场名称、地址、入口或明确导航词；
- 明确收费、免费时长、封顶价、优惠条件或实际支付记录；
- 车位数量、是否满位、排队、道路拥堵、车型限制或停车后步行路线；
- 评论中对上述事实的明确补充、修正或冲突提示。

疑问句只有在同一条评论或作者回复中同时出现明确答案时，才提取答案部分；疑问句本身永远不作为攻略内容。用户名和互动数字只能保留在来源元数据中，绝不能混入攻略正文。

### 6.3 输出前复检

每条清洗结果输出前，必须检查：

1. 删除用户名、平台控件和推荐流残留。
2. 删除以“吗、呢、吧、？”等结尾且没有事实答案的疑问句。
3. 删除只有情绪或评价、无法指导停车决策的句子。
4. 删除没有停车场归属的孤立价格和孤立数字。
5. 备注中每句话都要能回答“在哪里停、多少钱、怎么进、是否好停或有什么限制”中的至少一个问题。

## 七、最终停车攻略的固定字段

后续形成的用户可见停车攻略，只包含以下四部分：

### 1. 停车场名称

使用清洗、确认后的停车场正式名称。不得使用作者昵称、泛称、疑问句或“附近停车场”等无法识别的描述代替。

### 2. 收费明细

填写正文或评论中能够确认的收费标准、免费时长、封顶价、会员/消费/充电优惠和实际支付记录。不同类型的信息要分开表达，不能把实付金额反推成正式费率。

正文中的明确收费作为基础收费记录；评论中出现的不同价格不得直接覆盖基础收费，应转入“攻略正文”作为收费变化或现场核对提示。

### 3. 攻略正文

只放对停车决策有帮助的真实用户反馈，并改写成简洁、客观的攻略口吻，主要包括：

- 停车场到目的地的步行距离和路线；
- 入口、导航词、楼层或进出方向；
- 车位是否充足、是否容易排队、什么时段更紧张；
- 机械车位、车型、新能源车、推车等适配情况；
- 其他会影响停车选择的注意事项。

攻略正文不放收费明细、不放作者或评论用户名、不放无答案疑问句、不放与停车无关的内容。

### 4. 地点定位

地点定位是目标地点本身的可导航坐标，用于首页附近排序、地点详情页地图和“导航到目的地”。必须定位到目标地点的官方 POI、主要入口或用户实际到达的入口，不能用某个停车场坐标代替。地点名称、地址与地图 POI 不一致或存在多个同名候选时，先人工复核，不能直接选第一个结果。

### 5. 停车场定位

使用停车场本身或实际入口的 `lng`、`lat` 坐标，不使用目的地中心点代替。坐标无法可靠确认时显示“定位待补充”，并禁用导航能力；不得猜测坐标。

用户可见结构固定为：

```text
停车场：XXX
收费：XXX
攻略正文：XXX
停车场定位：XXX
```

来源链接、原笔记标题、作者、发布时间、采集时间、可信度、冲突标记、原始文件路径等字段继续保留在内部审核数据中，不作为用户可见攻略内容。

用户可见内容不得出现任何处理过程或来源提示，包括“正文中”“评论中”“原文”“笔记里”“作者回复”“有网友提到”“小红书上说”等表述。只输出整理后的停车事实、用户体验和必要的核对提醒；来源归因、证据位置和处理说明只保留在内部审核数据中。

## 八、最终入库数据标准

### 6.1 输出文件

每批处理完成后固定输出：

- `*-final.md`：给人审核的展示稿，严格只展示四个用户可见字段。
- `*-import.json`：给 `admin-import-guides` 使用的请求体，顶层必须是 `{ "places": [...] }`。
- 原始 JSON 和内部审核信息：继续留在本地，不进入用户可见字段。

默认只生成和本地校验 `*-import.json`，不自动执行云端新增；只有用户明确要求“导入/入库”时，才调用新增接口。

### 6.2 接口字段

```json
{
  "places": [
    {
      "name": "目标地点",
      "category": "景点",
      "city_code": "440100",
      "address": "可确认的地点地址",
      "district": "行政区",
      "summary": "地点本身的简短介绍",
      "area_tips": "汇总该地点全部停车场攻略的地点级停车总结",
      "lng": 113.260000,
      "lat": 23.130000,
      "coordinate_status": "已核验",
      "navigation_available": true,
      "coordinate_source": "地图 POI 及入口复核",
      "tags": [],
      "parkings": [
        {
          "name": "停车场名称",
          "fee_detail": "收费明细",
          "guide_text": "攻略正文",
          "location": "可搜索的导航词或地址",
          "lng": null,
          "lat": null,
          "coordinate_status": "待补充",
          "navigation_available": false,
          "fee_rules": [],
          "daily_cap": null,
          "night_flat": null,
          "confidence": "medium",
          "conflict_flag": false
        }
      ]
    }
  ]
}
```

必填规则：地点名称、地点分类、城市编码、地点地址、行政区、地点经纬度、停车场数组、停车场名称、收费明细或结构化收费规则、攻略正文、停车场定位和停车场经纬度都不能缺失。最终可落库数据中，用户可见字段不得保留 `null`、`undefined`、空字符串或字符串形式的 `"null"` / `"undefined"`。无法确认的内容不得猜测；应停止该条进入最终入库，或留在待补充草稿中。坐标属于最终入库必填的机器字段，不能再以 `coordinate_status: "待补充"` 进入正式数据。定位不能写“附近”“周边”等泛称，否则该条不通过校验。

### 6.6 入库前字段完整性

整理完成后必须按“地点层”和“停车场层”分别补齐信息：

- 地点层至少有：`name`、`category`、`city_code`、`address`、`district`、`summary`、`area_tips`、`tags`、`lng`、`lat`、`coordinate_status`、`navigation_available`、`parkings`。地点地址应使用可确认的道路、门牌、街区或官方地点地址；地点坐标应对应目标地点 POI 或主要入口，不能因为笔记主要描述停车场，就把地点坐标留空。
- `summary` 与 `area_tips` 必须分工：`summary` 是目标地点的简短介绍；`area_tips` 是把该地点全部停车场的攻略正文和已确认评论反馈进行二次归纳后的停车总览，不能只写“已整理N个停车点”，也不能只复制某一个停车场的攻略。
- 地点级停车总结只保留跨停车场有帮助的共性或对比信息，例如“周末车流集中”“不同入口步行距离差异明显”“立体车库需留意车型限制”；不能混入作者昵称、评论用户名、疑问句、孤立收费数字或未归属的零散内容。
- 停车场层至少有：`name`、`fee_detail` 或 `fee_rules`、`guide_text`、`location`。`location` 必须是可直接搜索的停车场名称、入口名称或具体地址，不能写“附近停车场”“周边车库”等泛称。
- 目标地点地址和停车场定位是两类不同字段：前者用于首页和详情页展示目标地点位置，后者用于用户搜索和后续坐标补充，不能相互替代。
- 地点坐标和停车场坐标必须分别检索、分别保存来源和核验时间；详情页的“导航”使用停车场坐标，地点级地图和附近排序使用地点坐标。
- 停车场坐标必须优先采用实际车辆入口坐标；地图 POI 中有 `entr_location` 或明确出入口坐标时优先使用，只有 POI 中没有入口坐标时才使用停车场 POI 坐标，并标记为“待核验”，完成地图路线复核后才能改为“已核验”。
- 导出 `*-import.json` 前执行空值扫描：递归检查所有用户可见字段；发现 `null`、`undefined`、空字符串或其字符串形式时，先补齐、删除该条或退回草稿，不得直接调用新增接口。
- 前端展示层也要做兜底：对可选字段使用空值隐藏或“待补充”提示，禁止把 JavaScript 空值直接渲染成 `null` / `undefined`。

### 6.3 收费结构化

`fee_detail` 是给用户看的完整收费说明；`fee_rules` 是给程序筛选和排序用的结构化规则。只对明确的收费事实生成规则，允许的 `rule_type` 为 `first`、`normal`、`cap`、`free`、`night`，允许的 `unit` 为 `hour`、`minute`、`day`、`time`。

- 每个停车场必须根据 `fee_rules` 自动计算 `min_price_hour`：仅取明确的 `first`/`normal` 小时价，`minute` 按 `price × 60 ÷ unit_minutes` 换算；单次收费、封顶价、优惠金额和无法换算为小时价的规则不得臆算。地点层 `min_price` 取所属车场中可计算小时价的最低值，避免列表或详情错误显示“价格待补充”。

- `fee_detail` 必须能单独让用户看懂金额、单位、时段、封顶或优惠条件；不能只写“基础收费”“白天收费”“有优惠”等没有价格的概括。
- `fee_rules.description` 只是规则标签，不能代替价格展示。前端展示时必须把 `price`、`unit`、`unit_minutes` 等字段拼成完整表述，例如“基础收费：5元/小时”“24小时封顶：70元/天”。

- 实付记录只写入 `fee_detail`，不得反推小时价。
- “首3小时”“超过后”“白天/夜间”“封顶”等条件要分别拆成规则；30分钟收费必须写 `unit: "minute"` 和 `unit_minutes: 30`。
- 会员、消费、充电等有触发条件的优惠写入 `fee_detail`，不能伪装成所有用户都适用的免费规则。
- 不同来源出现不同价格或封顶价时，不平均、不择一覆盖；`fee_detail` 保留差异，`conflict_flag: true`，正文写“近期有用户反馈……现场以当日公示为准”等不暴露来源的提示。
- 没有足够信息确定具体时段时，不能擅自补起止时间；可保留文字收费明细并把规则标为低可信或不生成该条规则。

### 6.4 攻略正文和来源隔离

攻略正文只能放距离、步行路线、入口、拥堵、排队、车位、机械车位、车型适配、预约、过夜和其他真实停车体验。收费数字统一放收费明细，正文只在收费有变化或冲突时补充必要的核对提醒。

禁止出现作者昵称、用户名、笔记标题、点赞数、评论原句、提问句和来源提示，例如“笔记中”“评论中”“原文”“作者回复”“小红书上说”“有人提到”“停车费是多少钱？”等。允许使用“有用户反馈/近期有用户反馈”作为产品化的不确定性表达，但不能写成用户可见的来源说明。

### 6.5 合并和定位

- 同一停车场跨多篇笔记只建一条记录，名称统一，收费和体验合并；冲突进入 `conflict_flag`。
- 同一停车场服务多个目标地点时，只选择一个主地点入库，避免 `p_parkings` 产生重复记录；其他目标地点的关系在审核稿中保留，待后续关系表支持后再扩展。
- 地点和停车场坐标都必须成对出现且在合法经纬度范围内；没有坐标或无法确认候选时，该条只能留在待补充草稿，不得进入最终 `*-import.json`。
- 地点与停车场都要记录 `coordinate_status`、`coordinate_source`、`coordinate_poi_name`、`coordinate_poi_id`、`coordinate_verified_at`。坐标来自 POI 中心而非实际入口时，必须保留这一事实，不能宣称“入口已确认”。

### 6.6 定位获取与核验流程

推荐采用“自动 POI 检索候选 + 名称地址匹配 + 入口核验”的流程；不再把逐个 `wx.chooseLocation` 作为批量主流程，微信地图人工选点只用于处理自动检索无法确认的少量记录：

1. 批量自动检索优先使用腾讯位置服务 WebService 的地点搜索/地理编码能力：地点用“广州 + 目标地点名称”，停车场用“广州 + 停车场名称 + 目标地点名称”，并限制广州区域。API Key 只放在服务端或本地受保护配置中，不进入小程序前端和提交仓库。
2. 自动匹配不能只取搜索结果第一条。按名称相似度、地址与行政区、地点关联关系、POI 类型（停车场/停车库）综合评分；最高候选与第二候选分差不足时进入人工复核队列。
3. 自动返回的 POI 坐标先标为“待核验”。停车场坐标若只代表 POI 中心，不得直接写成“实际入口”；可继续用“停车场出入口”“停车场入口”等关键词检索入口候选，仍无法确认时使用微信 `wx.chooseLocation` 进行补点。
4. 地点坐标优先选择官方地点 POI 或主要到达入口；停车场坐标优先选择车辆实际驶入的道闸/车库入口，不能使用目的地中心、停车场建筑中心或道路中点代替。
5. `wx.getLocation` 只允许用于记录管理员当前所在位置，不能根据它推断目标地点或停车场坐标；`wx.openLocation` 只用于查看导航，不能当作坐标采集接口。`wx.chooseLocation` 返回的位置只能作为人工确认结果保存。
6. 自动候选通过人工快速复核后，保存 `coordinate_source`、`coordinate_poi_name`、`coordinate_poi_id`、`coordinate_verified_at` 和 `entrance_verified`；只有确认名称、地址、道路方向和攻略步行路线一致，才改为“已核验”。
7. 出现多个候选、名称只有泛称、候选落在错误行政区或地图找不到对应 POI，均标记为待补充，不能强行填坐标。每批处理后生成坐标核验清单；当前项目正式入库要求地点和停车场坐标全部为“已核验”。

### 6.7 腾讯位置服务配置

批量定位使用腾讯位置服务 WebService API。另一台电脑执行定位脚本前，在本地配置以下 Key，并确认已启用地点搜索/地理编码能力：

```text
TENCENT_MAP_KEY=<在本机私密配置中填写，不要提交到 Git>
```

Key 只用于定位候选检索，不得写入小程序前端代码；如果规则文件被公开分享或提交到公共仓库，应立即在腾讯位置服务控制台限制来源或重新生成 Key。

## 九、自动入库前校验

生成 JSON 后必须自动校验，校验不通过就停止在本地，不调用新增接口。至少检查：

1. 地点名称唯一，停车场名称在同一批次全局唯一且不为空；每个地点至少有一条停车场。
2. 收费明细或 `fee_rules` 至少有一项；每条规则价格为非负数字，单位和类型合法，半小时规则带有 `unit_minutes`。
3. `area_tips`、攻略正文和定位非空；定位不是“附近/周边/某个停车场”等泛称。
4. 坐标成对、范围合法，并与 `coordinate_status`、`navigation_available` 一致。
5. 用户可见字段不含来源词、用户名、页面噪声、纯提问和与停车无关的内容。
6. 收费冲突、低可信收费和待补坐标必须显式标记，不能静默丢弃或改写成确定事实。

校验通过后，输出“可导入”状态和请求文件路径；仍需用户明确授权后才执行云端写入。

## 十、用户反馈转化为攻略

停车攻略的价值不仅是列出停车场和收费，还要把用户实际停车过程中遇到的情况转化为简洁、可执行的提示。用户反馈可以成为攻略正文的一部分，但必须经过忠实改写。

### 8.1 改写原则

1. 保留反馈中的事实、条件、程度和限制，不改变原意，不凭空增加结论。
2. 将口语化经历改写为面向停车决策的描述，例如把“每次都要排队很久”整理为“车位较少，高峰期可能需要排队”。
3. 只写停车相关结果，不保留作者昵称、第一人称、情绪化表达、标签和原文句式。
4. 单次体验、个别评论或带有“好像/大概/感觉”的内容，使用“有反馈”“可能”“建议现场确认”等程度较弱的表达，不能写成确定规则。
5. 多条反馈方向一致时，可以合并为一条更简洁的实用提示，但不能扩大反馈范围或虚构普遍性。
6. 收费数字、优惠条件和用户体验分开：收费栏写明确价格，攻略正文写拥堵、车位、入口、机械车位、车型适配和路线等决策信息。
7. 对外展示时不写“某博主称”“网友表示”“小红书上说”，但内部原始数据和来源记录必须保留。

### 8.2 评论区整体清洗与提取

评论区不是只用于补充收费变化，而是“真实停车体验”的重要来源。处理每篇笔记时，应阅读已采集到的评论及作者回复，整体提取其中对停车决策有帮助的信息，并改写后放入对应停车场的“攻略正文”。

可以提取的评论信息包括：

- 实际收费变化、实付金额、封顶价、优惠是否仍然有效；
- 哪个时段容易满位、是否需要排队、是否存在临时管制；
- 入口是否容易找、道路是否拥堵、进出是否方便；
- 停车后实际步行距离、步行路线、适合哪个目的地入口；
- 是否需要预约、是否能过夜、是否适合新能源车或较大车型；
- 对正文信息的明确补充、纠正或与正文收费/体验相冲突的反馈。

处理时遵循以下规则：

1. 评论中的有效体验可以成为攻略正文的一部分，但必须改写成简洁、客观、可执行的停车提示，不复制评论原句。
2. 已知收费为“5元/小时”，近期有用户反馈可能已调整为“4元/小时”时，收费明细仍保留“5元/小时”；攻略正文补充“近期有用户反馈收费可能已调整为4元/小时，现场缴费前请留意公示”。
3. 评论有明确日期时，优先写具体时间，例如“2026年4月有用户反馈收费可能已调整为4元/小时”。没有日期时，使用“有用户反馈”或“近期有用户反馈”等产品化表述；只有在确实无法判断新旧时，才不使用“近期”。
4. 评论只反映个别体验时，使用“有用户反馈”“近期有用户反馈”“可能”等限定词，不写成当前统一规则。例如“有用户反映工作日10点后车位变少”可以整理为“工作日上午10点后可能开始紧张，建议预留排队时间”。
5. 作者对评论的直接回复可以作为补充信息，但仍按用户反馈处理，不能自动视为官方确认。
6. 多条评论方向一致时，可以合并为一条攻略提示；互相矛盾时，攻略正文提示“存在不同反馈，现场以当日情况为准”，内部数据保留冲突记录。
7. 评论中的有效信息放入攻略正文，不在用户可见内容中展示评论用户名、作者昵称、评论原句、点赞数或回复数。
8. 只有提问、没有明确答案的评论不提取；如果评论提问后有直接且具体的回答，只提取回答中的有效事实。

### 8.3 推荐表达结构

```text
停车场：停车场名称
收费：明确收费标准、实付记录或优惠条件
攻略正文：把用户反馈改写成停车决策提示
```

攻略正文优先回答：是否容易停、什么时候容易满、是否需要排队、是否适合新能源车、是否为机械车位、入口是否容易错过、停车后怎么到目的地。

### 8.4 示例

原始反馈整理后可以写成：

```text
停车场：市妇幼停车场
收费：3小时内7.5元/小时，3小时后15元/小时。
攻略正文：这里道路拥堵、车位少、排队时间长，基本为机械车位，对新能源车不太友好，谨慎考虑。

停车场：粤海天地停车场
收费：12元/小时。注册会员每月可领取3小时停车券；消费可获得1小时券；周末首次进场可免费2小时；积分可兑换停车券。每天减免最多3小时。
攻略正文：B3机械车位较多，建议尝试B4。
```

上述示例中，收费和优惠条件保持原始信息；攻略正文只保留对停车选择有帮助的真实反馈，并改为简洁的攻略口吻。
