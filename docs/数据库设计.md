# 停车攻略小程序 · 数据库设计

> 版本 v1.0 ｜ 2026-09-09
> 设计目标：先跑通广州，同时从第一天就按「全国 300+ 城市、百万级数据」的规模设计，避免后期重构。

---

## 一、数据量估算与容量规划

| 对象 | 单城均值 | 50 城 | 300 城（远期） | 说明 |
| --- | --- | --- | --- | --- |
| 目的地 place | 80 | 4,000 | 24,000 | 景点/商圈/医院/枢纽/学校 |
| 停车场 parking | 300 | 15,000 | 90,000 | 每 place 3-5 个 |
| 收费规则 fee_rule | 1,200 | 60,000 | 360,000 | 每 parking 3-5 条 |
| 攻略提示 tip | 400 | 20,000 | 120,000 | 含用户投稿 |
| 用户上报 price_report | — | 持续增长 | 千万级 | 高频写入，单独放 |

**结论**：单表千万级以内，MySQL 8 单库完全够用，不需要一开始就分库分表。但设计上必须预留分片键（`city_id`），将来按城市水平拆分时零改造。

---

## 二、核心设计决策（为什么这么设计）

### 1. 收费规则独立成表，而不是塞 JSON
停车场收费是**分时段的阶梯规则**：首小时 10 元、后续 5 元/h、24 小时封顶 60、夜间 22:00-08:00 一口价 20、消费满 200 免 2 小时……

如果用 JSON 字段存，就没法做「按价格排序」「筛选 24 小时封顶 50 以内的车场」这类核心查询，而这些正是用户最需要的功能。所以拆成 `fee_rules` 表，用时间区间 + 优先级表达任意复杂规则。

### 2. 目的地与停车场多对多
一个停车场往往服务多个目的地（正佳广场停车场同时也服务体育西路商圈），一个目的地也对应多个停车场。用 `place_parking` 中间表存步行距离/时间，后期做「停 A 走 300 米去 B 更便宜」的推荐就靠它。

### 3. 全表带 `city_id`，作为逻辑分片键
所有业务表冗余 `city_id`。将来数据量上来按城市分片，或做「按城市独立库」，都不用改查询逻辑。

### 4. 地理查询：`geohash` + 经纬度，不上 PostGIS
附近车场查询用 geohash 前缀匹配先粗筛，再用 Haversine 精算距离。geohash 前缀 5 位约 5km×5km，配合 `city_id` 索引，百万数据毫秒级。避免一上来引入 PostGIS 增加运维成本。

### 5. 数据可信度内建
停车场带 `confidence`（high/medium/low）、`source`、`verified_at`。前端对低置信数据显示「仅供参考，以现场为准」，并引导用户上报实价。数据可以自我进化，这是爬不来的核心价值。

### 6. 中文模糊搜索
MySQL 8 用 `FULLTEXT` + `ngram` 分词解析器（中文必需）。SQLite 开发期用 `LIKE` 兜底。预留 `search_logs` 记录用户搜了但没结果的热词——这是补数据的风向标。

### 3.6 fee_rules 收费规则 ★核心表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| parking_id | BIGINT NOT NULL | |
| rule_type | VARCHAR(16) | first(首段)/normal(常规)/night(夜间)/cap(封顶)/package(包月)/discount(优惠) |
| start_minute | INT | 起始分钟（从入场算起） |
| end_minute | INT | 结束分钟，NULL 表示不限 |
| time_start | TIME | 时段起点，如 22:00（夜间规则用） |
| time_end | TIME | 时段终点，如 08:00 |
| price | DECIMAL(8,2) NOT NULL | 价格 |
| unit | VARCHAR(8) | hour 小时 / time 次 / day 天 / month 月 |
| unit_minutes | SMALLINT | 计费单位（分钟），如 30 表示每 30 分钟一跳 |
| priority | TINYINT DEFAULT 0 | 优先级，越大越优先匹配 |
| description | VARCHAR(255) | 人类可读：首小时10元，后续5元/小时 |
| confidence | ENUM | 该条规则的可信度 |

索引：`idx_parking (parking_id, priority)`

**能表达的计费场景举例**：
```
首2小时: start=0 end=120 price=10 unit=hour unit_minutes=60
第3小时起: start=120 end=NULL price=5 unit=hour unit_minutes=60
24h封顶: rule_type=cap price=60
夜间: rule_type=night time_start=22:00 time_end=08:00 price=20 unit=time
```
前端可以用这套规则做一个「停车费计算器」——用户输入停多久，直接算出来要多少钱。这是差异化的杀手锏功能。

## 四、扩展性设计

### 分库分表路径
1. **阶段一（0-100 万行）**：单库单表 + 索引优化，MySQL 8 无压力
2. **阶段二（100-1000 万）**：读写分离 + Redis 缓存热门城市数据
3. **阶段三（千万+）**：按 `city_id` 水平分片，热点城市（北上广深）单独分库
   - 所有表已冗余 `city_id`，分片时无需改业务代码
   - 跨城市查询（如全国搜索）走 ES 或汇总表

### 缓存策略（Redis）
| Key | 内容 | 过期 |
| --- | --- | --- |
| `city:{id}:hot_places` | 城市热门目的地 | 1h |
| `place:{id}:detail` | 目的地详情 + 停车场列表 | 30min |
| `search:{city}:{keyword}` | 搜索结果 | 10min |
| `nearby:{geohash5}` | 附近车场 | 5min |

### 搜索演进
1. 初期：MySQL FULLTEXT ngram
2. 中期：接入微信云开发搜索 / Elasticsearch，支持拼音搜索（"bjl" → 北京路）
3. 搜索词库：从 `search_logs` 挖掘热词，建立同义词表（"省医" → 广东省人民医院）

### 数据更新机制
- 官方数据（政府价目表）：季度全量核验
- 用户上报：实时审核，采纳后更新 `verified_at`
- 超过 180 天未核实的停车场，前端自动标注「信息可能过期，求实测反馈」
